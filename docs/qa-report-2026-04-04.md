# Relatório de QA — Sistema de Reserva de Mesa (Desk Booking)

> Análise executada em: 04/04/2026 | Branch: `main`
> Tipo: Revisão de produto (bugs + experiência do usuário)

---

## BUGS CRÍTICOS

### B1 — Timezone: usuário não consegue reservar "hoje" após 21h (horário de Brasília)
**Onde:** `routes/bookings.js:209`
```js
const today = new Date().toISOString().split("T")[0]; // UTC
if (date < today) → "Não é possível reservar para datas passadas"
```
**Cenário:** João tenta às 21:30 do dia 04/04/2026 reservar para "hoje" (04/04). O servidor UTC já está em 05/04 → retorna erro "data passada". Entre 21:00–23:59 (Brasília), a reserva para o próprio dia é bloqueada incorretamente.

---

### B2 — Admin pode criar reserva para qualquer data futura (sem limite de 4 semanas)
**Onde:** `routes/bookings.js:315` (`POST /bookings/admin`)
O endpoint de admin não tem a verificação `if (new Date(date) > _maxD)` presente no endpoint normal. Testando com data `2035-06-15` (segunda-feira): é aceita sem erro.

---

### B3 — Backend não bloqueia declaração TI para datas passadas
**Onde:** `routes/ti.js:97–104`
Só verifica `reqDate > maxDate` (limite futuro). Não verifica se `reqDate < today`.
**Cenário:** Via API direta: `POST /api/ti/schedule { date: "2026-01-05", location: "home" }` → aceito. Isso suja o histórico e pode disparar cancelamento de reservas passadas (`cancelBookingForDate`).

---

## BUGS MÉDIOS

### B4 — Desativar mesa deixa reservas existentes em estado fantasma
**Onde:** `admin.js:toggleDesk` + `routes/desks.js:66–70`
Ao desativar a mesa 03, reservas futuras nela não são canceladas. O SVG renderiza o assento como "inactive" independente de ter reserva, então o usuário vê a mesa inativa mas ainda encontra a reserva em "Minhas Reservas". Inconsistência total.

---

### B5 — `toggleAdmin` e `toggleTi` executam sem confirmação
**Onde:** `admin.js:521–529` e `531–538`
Um misclick no botão "Tornar Admin" promove o usuário instantaneamente. Não há `confirm()` nem modal de confirmação. Risco de erro em produção.

---

### B6 — Ações `create_user` e `set_weekly_days` aparecem como texto cru no audit log
**Onde:** `routes/audit.js:6–13`
```js
const ACTION_LABELS = {
  cancel_booking: ...,
  create_booking_admin: ...,
  // "create_user" não está mapeado
  // "set_weekly_days" não está mapeado
};
```
Essas ações caem no fallback `l.action` e aparecem como `create_user` / `set_weekly_days` sem tradução para o admin.

---

### B7 — SVG renderiza no máximo 10 mesas em silêncio
**Onde:** `app.js:79–80`
```js
const leftDesks  = sorted.slice(0, 5);
const rightDesks = sorted.slice(5, 10);
```
Se o admin criar a mesa 11 (e houver reserva nela), ela simplesmente não aparece no mapa. Nenhum aviso.

---

### B8 — Export CSV sem validação de intervalo de datas invertido
**Onde:** `admin.js:exportCSV()` e `exportTiCSV()`
Testando com `from: 2026-12-31` e `to: 2026-01-01`: retorna CSV com apenas o cabeçalho, zero linhas, sem mensagem de erro. Usuário pensa que não há dados.

---

## BUGS LEVES

### B9 — Selecionar fim de semana no date input reseta para "hoje" (não para a próxima segunda)
**Onde:** `app.js:20–23`
Usuário seleciona sábado 11/04 querendo ir para a semana de 14/04 → app reseta para 04/04 (hoje). Comportamento esperado: avançar para segunda-feira 13/04.

---

### B10 — Tokens de refresh acumulam ao atualizar perfil
**Onde:** `routes/auth.js:143`
`PUT /auth/profile` chama `issueTokens()` sempre, gerando novo refresh token. O token antigo não é invalidado. Cada update de perfil acumula um token na tabela `refresh_tokens`.

---

### B11 — Ao excluir usuário, tokens de refresh ficam órfãos no banco
**Onde:** `routes/users.js:100`
`DELETE FROM users` não tem `DELETE FROM refresh_tokens WHERE user_id = ?`. Os tokens ficam na tabela indefinidamente.

---

### B12 — Senha nova não é validada no frontend antes de enviar ao servidor
**Onde:** `app.js:400–404`
Não há validação client-side que confirme se `password === confirmPassword` antes de enviar. O erro só aparece via toast após a requisição falhar, gerando uma round-trip desnecessária ao servidor.

---

## PROBLEMAS DE UX

### U1 — Usuário não sabe quantas reservas ainda pode fazer na semana
Não há indicador de "2/3 dias usados esta semana". O usuário só descobre o limite quando toma o erro. Sugestão: contador visível no header do app.

---

### U2 — Membro TI ao marcar SP é redirecionado à força após 1.8s
**Onde:** `ti.js:182–184`
```js
setTimeout(() => { window.location.href = `/app.html?date=${pickerDate}`; }, 1800);
```
Se o usuário já tem mesa reservada, o toast mostra "SP confirmado" mas mesmo assim redireciona. Se o usuário queria continuar na grade TI, é levado embora sem chance de cancelar.

---

### U3 — Admin não tem filtro de data/usuário na aba Reservas
A listagem de reservas é cronológica paginada. Para achar a reserva de "João para 10/04", o admin precisa percorrer páginas. Nenhum campo de busca ou filtro de data.

---

### U4 — Dois usuários com mesmo primeiro nome ficam indistinguíveis no SVG
"Carlos Silva" e "Carlos Mendes" → ambos aparecem como "Carlos" no assento. O tooltip (`<title>`) mostra o nome completo, mas é invisível em telas touch.

---

### U5 — Dashboard usa 22 dias úteis hardcoded para calcular taxa de ocupação
**Onde:** `admin.js:125`
```js
const WORKING_DAYS = 22;
```
Em meses com feriados ou menos semanas, o cálculo superestima ou subestima a ocupação sem refletir os dias reais trabalhados.

---

### U6 — Nenhum aviso de impacto ao desativar mesa com reservas futuras
Ao clicar "Desativar" na mesa 03 que tem 5 reservas nesta semana, nenhum alerta informa quantas pessoas serão afetadas. O comportamento de "Desativar" (reserva fica como fantasma) e "Excluir" (reserva é cancelada) é muito diferente, mas ambos parecem igualmente seguros na interface.

---

### U7 — Audit Log sem filtros (data, tipo de ação, ator)
Com centenas de ações, o admin navega por paginação simples sem poder filtrar por "quem fez o quê" ou "ações desta semana".

---

### U8 — Modal de localização TI (admin) fecha ao clicar no backdrop sem confirmação
**Onde:** `admin.js:680–683`
O admin pode clicar fora sem querer e perder a seleção em andamento. Nenhum feedback de "ação cancelada".

---

### U9 — Minha Semana: sem acesso rápido para declarar localização TI
Membros TI em `myweek.html` veem "— Livre" com link "Reservar" para `app.html`, mas para declarar Home ou Itaquá precisam navegar para `ti.html` separadamente. A tela Minha Semana poderia integrar o seletor de localização inline.

---

### U10 — Redirecionamento forçado ao marcar SP não pode ser cancelado
**Onde:** `ti.js:182–184`
O toast informa que o usuário será redirecionado, mas não oferece botão "Ficar aqui" ou "Cancelar". O tempo de 1.8s é curto demais para leitura em mobile.

---

### U11 — Aba "Reservas" do admin (Anterior/Próximo) sem numeração de páginas
A paginação da aba Reservas usa apenas "Anterior / Próximo" sem indicar o número total de páginas ou permitir saltar para uma página específica. A aba Auditoria tem botões numerados — inconsistência.

---

### U12 — Usuário não é notificado quando admin altera seus dados ou cancela sua reserva
Admin pode alterar `weekly_office_days`, status TI, cancelar reserva — o usuário afetado não recebe nenhum aviso (o serviço de e-mail foi removido no commit 165da73). O usuário só percebe ao tentar fazer algo e tomar um erro diferente do esperado.
